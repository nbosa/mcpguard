# 安全模型 — mcp-guard v0.6.0

> English version: [../en/security.md](../en/security.md)

## 1. mcp-guard 是什么

mcp-guard 是一层**检测与审计**组件。它读取 MCP 智能体发往工具的请求以及工具返回的内容，
并报告与既定策略之间的偏差。

## 2. mcp-guard 不是什么

* 它**不是沙箱**，不会限制工具的权限。
* 它**不是防火墙**，不会接管网络通信。
* 它**不能替代操作系统层面的隔离**。在不受信任的工具与宿主机之间，仍然应该有容器、
  seccomp 配置和只读文件系统。
* 它**无法阻止**控制了智能体二进制文件的攻击者。它只报告智能体的行为，不会约束它。

请把 mcp-guard 当作额外的绊线，而不是一道防线。

## 3. 威胁模型

| 攻击者 | 能力 | mcp-guard 能看到什么 |
| --- | --- | --- |
| **恶意工具服务端** | 控制它返回的工具输出 | ANSI 序列、隐藏文本、凭据材料、载荷中的金丝雀 |
| **被篡改的工具描述** | 修改线上工具的描述或 schema | schema 漂移、新增必填参数、被改写的描述 |
| **被提示词注入的智能体** | 用攻击者选定的参数发起工具调用 | 路径穿越、凭据路径、金丝雀与机密外发 |
| **精心构造载荷的人** | 自由选择路径或字符串的写法 | 规范化会消除写法差异：编码穿越、ADS、保留设备名 |

不在范围内：针对宿主操作系统的攻击、针对 mcp-guard 进程本身的攻击，
以及需要攻击者同时控制策略文件的攻击。

## 4. 信任边界

```
        ┌──────────────── 受信任：你的策略、已固定的清单 ──────────────────────────┐
        │                                                                          │
  智能体 │   调用 / 参数                     返回内容 / 载荷                    │ mcp-guard
   ─────┤──────────────────────────────► ───────────────────────────────►       ├────►
        │                                                                          │
        └──────────────── 不可信：来自工具侧的一切 ────────────────────────────────┘
```

mcp-guard 把工具侧的一切都视为敌意输入。整个工具的设计前提是：它可以安全地运行在
攻击者控制的字符串上。

## 5. 实现层面的性质

### 5.1 无副作用

路径规范化完全是词法层面的：没有 `open`，没有 `stat`，没有 `os.path.realpath`，
不解析符号链接，也不联网。整个护栏不会因为一条构造出来的路径就去碰文件系统。

整个工具中唯一的文件访问，是读取策略、transcript 以及 ETDI / 固定清单文件——
这些路径都由操作者指定，而不是由载荷指定。

### 5.2 证据脱敏

发现项会引用有问题的载荷，而其中往往正包含护栏要保护的那份机密。每条发现项的证据
在离开引擎之前都会经过 `core.redact.redact()`。已知的凭据材料（AWS 密钥、
GitHub 与 Slack 令牌、私钥块、JWT、内嵌凭据的 URL、被赋值的机密）会被替换为
`<redacted:kind>` 标记。

随后证据会被截断到 `settings.max_evidence_chars`，控制字符会被转义，
因此报告可以安全地打印到终端或写入日志。

只有在确实需要查看原始证据时才设置 `redact_evidence = false`——并要明白，
那样这份报告本身就变成了机密。

### 5.3 确定性

规则求值没有随机性，不依赖时钟，也不联网。相同输入总是产生相同顺序的相同发现项。
这正是固定清单可复现、审计日志可比较的原因。

系统中唯一的时间戳是固定清单中的 `generated_at`，且由调用方提供。

### 5.4 显式失败，而不是静默

抛出异常的插件会被转换成 `ENGINE-000` 发现项。运行继续，报告仍然列出其他所有发现项，
审计链也会记录下「某项检查未能完成」。崩溃绝不会变成「没有发现项」。

### 5.5 默认失败关闭

* 默认策略在 `HIGH` 级别失败。
* `settings.etdi.require_pins` 默认为 `true`：没有固定清单的 ETDI 文档本身就是一条
  发现项（`ETDI-008`）。
* `settings.canary.block_on_match` 默认为 `true`。
* 路径插件对凭据路径（`PATH-002`，`CRITICAL`）和基础目录逃逸（`PATH-001`，`CRITICAL`）
  判定为失败。

### 5.6 策略完整性

策略的可信度取决于它所在文件的可信度。`policy-lint` 会报告未知插件、未知规则编号、
非法正则和类型错误，因此策略里的笔误会以错误的形式暴露出来，而不是悄悄让某项防护失效。

## 6. 已知限制

1. **仅做词法分析。** 在不访问文件系统的前提下无法解析 `~/link-to-etc`。
   请改用 `allowed_roots` 来约束可达路径集合。
2. **URL 不是路径。** `https://host/%2e%2e/etc` 不会被路径规则检查，
   但仍然会被金丝雀规则扫描。
3. **熵是启发式的。** `CANARY-004` 迟早会在合法的高熵字符串上误报，
   例如哈希值或压缩后的静态资源。请调整 `entropy_threshold` / `min_blob_len`，
   或者降低其级别。
4. **外发判定依赖命名。** `CANARY-008` 只会对 `settings.canary.egress_tools` 中列出的
   工具触发。请保持该列表是最新的。
5. **描述审阅仍然是人的工作。** 固定能检测到描述发生了变化，但无法判断新的描述是否安全。
   请阅读 diff。
6. **无法保护工具侧。** 如果服务端在返回内容中说谎，而这种谎言不匹配任何规则，
   mcp-guard 也无能为力。

## 7. 上报一条发现项

发现项的设计目标是能直接放进工单。每条都带有稳定的规则编号、严重级别、位置
（`calls[2].arguments.path`）、经过脱敏的证据字符串以及修复建议。
规则编号在各个版本之间保持稳定，可以用来抑制、升级或跟踪某一项检查。
